## Context

The application uses a multi-tenant architecture where each tenant has its own schema in PostgreSQL. Currently, user registration creates a `User` record in the `public` schema and then executes a `CREATE SCHEMA` command. This change extends this flow to include the creation of a baseline set of tables (e.g., `notes`) within the newly created schema.

## Goals / Non-Goals

**Goals:**
- Automate the creation of a standard `notes` table for every new tenant.
- Ensure the `notes` table is created immediately after the schema is created during registration.
- Provide a robust mechanism for executing DDL statements in a specific tenant schema.

**Non-Goals:**
- Handling migrations for existing tenants (this change focus on new registrations).
- Implementing a full-blown migration engine for tenant schemas.

## Decisions

- **Decision 1: DDL Execution via Prisma `$executeRawUnsafe`**
  - **Rationale**: Dynamic schema-specific DDL is best handled via raw SQL as Prisma's standard client is tied to a fixed schema definition at build time.
  - **Alternative**: Programmatic use of Prisma Migrate. *Rejected* due to complexity and performance overhead during a web request.

- **Decision 2: Encapsulation in `TenantProvisioningService`**
  - **Rationale**: Creating a dedicated service for provisioning keeps the `UserService` (or registration logic) clean and allows for easier testing and expansion of the provisioning logic.

- **Decision 3: Sequential Execution**
  - **Rationale**: The flow will be: Create User -> Create Schema -> Provision Tables. This ensures that the schema exists before we try to create tables in it.

## Risks / Trade-offs

- **[Risk]** Partial failure: Schema is created but tables fail to provision.
  - **Mitigation**: The registration process should treat provisioning failure as a critical error, potentially rolling back the user creation or marking it as "Incomplete".
- **[Risk]** SQL Injection in schema names.
  - **Mitigation**: Ensure schema names are strictly validated (which they should be already as they are generated by the system).
